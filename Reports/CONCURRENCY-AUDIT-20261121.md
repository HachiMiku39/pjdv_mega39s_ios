## 发布前优先处理

**P1 · 两个窗口可同时进入游戏准备阶段。** iPad／Mac 的启动窗口各自检查原生会话是否空闲。原生的独占检查发生在准备工作完成之后。若窗口 A 建好了 AutoPlay 临时存档并开始游戏，而窗口 B 随后因所选 Mod 不可用而启动失败，B 的清理会关闭 A 的 AutoPlay，并删除 A 正在使用的临时存档。

隔离测试执行了实际的 Swift 启动和清理代码，用替身控制原生启动、音频及资源查找。测试观测到 A 的临时存档从存在变为不存在，普通存档样本仍然一致。真机双窗口表现待验。修复应在设置输入、渲染图层和存档之前取得进程级会话所有权，直到对应会话完成清理才释放。需要覆盖启动失败重试、关闭拥有会话的窗口和重新连接窗口。复核入口为 `Sources/App.swift` 的 `startGame`、`Sources/GuestRuntime.swift` 的 `validateMapping` 与 `AutoPlaySession.end`、`Runtime/dm/host/pjdv_boot.c` 的 `pjdv_guest_boot`。

| Metal 显示链启停与退出 | 显示线程刚启动，下一帧确认前就关闭时，停止请求可能丢失。退出时还可能漏等正在编码、尚未提交的最后一帧。现在由显示线程确认图层释放，清理前等待编码与已提交回调结束。 | 真实线程和运行循环配合可控显示回调，完成 100 次交错停止、1,000 轮帧率切换，并测试延迟提交／完成。 |
| Metal 每帧资源复用 | 合并或丢弃排队帧会推进队列票号，旧逻辑据此允许 CPU 改写 GPU 仍在读取的 UV／HDR 缓冲。现在每个槽位由对应的 GPU 完成回调释放，提交前编码失败也会归还槽位。 | 两条 Metal API 分支均覆盖延迟完成、错误完成、其他槽位独立推进及编码失败恢复，ASan／UBSan 通过。GPU 回调由测试控制。 |

## 验证范围

iOS 与 Mac Catalyst 的 Release 目标均构建通过。线程和文件交错在 Mac 上使用项目源码、合成文件以及隔离存档验证。ThreadSanitizer、AddressSanitizer 和 UndefinedBehaviorSanitizer 的结果分别对应上表的局部用例。本轮未在 iPad 上重装、整曲压测或采集真实 GPU 帧，也没有将用户先前报告的掉帧、黑屏或卡键归因于这些竞态。
